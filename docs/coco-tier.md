# Confidential containers tier (`coco`)

The `coco` tier installs OpenShift sandboxed containers with peer pods on an AWS cluster. A pod that uses the RuntimeClass `kata-remote` runs in its own EC2 instance (a pod VM) with AMD SEV-SNP. This page is for operators who provision and deprovision `coco` clusters through the fleet pipelines.

The cluster overlay is generated by [fleet-cluster-scaffold](https://github.com/redhat-openshift-partner-labs/fleet-cluster-scaffold) with `--tier coco`. Its README section "Confidential containers tier (--tier coco)" describes the overlay, the peer-pods IAM policy and the pipeline contract that the tasks below implement.

## Prerequisites

| Prerequisite | Requirement |
|---|---|
| OpenShift version | 4.22.11 or later on 4.22, or 4.21.24 or later on 4.21. The scaffold default image set `img4.22.22-multi-appsub` meets it. A custom `--image-set` is not checked. |
| Region | `us-east-2` or `eu-west-1`. The scaffold rejects other regions. |
| Import role | The overlay is rendered by a fleet-cluster-scaffold version that creates the IAM role `<name>-vmimport-role` and gives the installer policy `iam:PassRole` on it. An overlay without the role fails in `build-podvm-image-aws`; regenerate it. |
| Hub | The Tekton definitions under `tekton/` and the pipeline image (`pipeline-image` in `fleet-pipeline-config`) include the `coco` tasks before a `coco` overlay is merged into fleet-clusters. The pipeline image contains `qemu-img`. |
| Hub node storage | `build-podvm-image-aws` extracts and converts the pod VM disk in an `emptyDir` volume, which uses the ephemeral storage of the hub node that runs the task. |

## Pod VM image

fleet builds one pod VM AMI per cluster. `build-podvm-image-aws` builds it in post-provision, on the hub, with the cluster's installer credential (see [Post-provision](#post-provision)). `terminate-pod-vms` deletes it in deprovision (see [Deprovision](#deprovision)).

| Item | Value |
|---|---|
| Disk image | The related image of the package `sandboxed-containers-operator` (channel `stable`, catalog `redhat-operators`, read from the spoke's PackageManifest) whose repository ends in `openshift-sandboxed-containers/osc-dm-verity-image` and that is pinned by digest. |
| Payload | The digest of the disk image, `sha256:<hex>`. |
| Disk file | `/image/podvm.qcow2` in the disk image. |
| AMI name | `<name>-podvm-<first 12 hex characters of the payload>` |
| AMI settings | `x86_64`, `hvm`, ENA, boot mode `uefi`, TPM 2.0, root device `/dev/xvda`. These are the settings of the operator's own image creation. |
| Tags on the AMI and on its snapshot | `openshiftpartnerlabs.com/cluster=<name>` and `openshiftpartnerlabs.com/podvm-payload=<payload>`. The cluster's peer-pods IAM policy allows instance launches only from an image and a snapshot that carry the first tag. |
| Staging bucket | `<infraID>-podvm-image` in the cluster's region, all public access blocked, object `podvm.raw`. The build deletes the bucket when it ends. |
| Import role | `<name>-vmimport-role`, passed to `ec2 ImportSnapshot` as `RoleName`. |

A post-provision run reuses what an earlier run built for the same payload: an available AMI with both tags is returned, and a completed snapshot with both tags is registered without a new import. A run builds a new AMI when the catalog names a disk image with another digest. The AMI of the earlier digest stays in the account until deprovision.

`apply-coco-workloads` checks, after the operator is installed, that the installed version names the disk image the AMI was built from (step 7 under [Post-provision](#post-provision)).

List the pod VM AMIs of a cluster:

```bash
aws ec2 describe-images --region us-east-2 --owners self --filters "Name=tag:openshiftpartnerlabs.com/cluster,Values=<name>" "Name=tag-key,Values=openshiftpartnerlabs.com/podvm-payload" --query 'Images[].[ImageId,Name,State,CreationDate]' --output table
```

## Create the overlay

```bash
fleet-scaffold-cluster aws --name coco-east-01 --region us-east-2 --tier coco --podvm-instance-type m6a.xlarge
```

Compared with a scoped overlay of another tier, a `coco` overlay has:

- one more Crossplane AccessKey, `<name>-peer-pods-access-key`, which writes the Secret `<name>-peer-pods-credentials-raw` on the hub. It carries the three target annotations (`credentials-request: openshift-sandboxed-containers-aws`, `target-namespace: openshift-sandboxed-containers-operator`, `target-secret: peer-pods-secret`) and `openshiftpartnerlabs.com/delivery: post-provision`;
- one more IAM Role, `<name>-vmimport-role`, with the inline policy `<name>-vmimport-policy`. The service `vmie.amazonaws.com` assumes it to read the bucket `<infraID>-podvm-image`. The installer policy has `iam:PassRole` on it;
- the key `podvm-instance-type` in `metadata.yaml` (see [per-cluster-metadata.md](per-cluster-metadata.md));
- the ManagedCluster label `tier: coco`.

## What the pipelines do

### Pre-provision

| Task | Behavior for a `coco` overlay |
|---|---|
| `wait-for-aws-component-credentials` | Waits for `<name>-peer-pods-credentials-raw` together with the operators' raw Secrets. |
| `build-aws-credentials-manifests` | Leaves the peer-pods credential out of `<name>-cloud-credentials-manifests` and logs `Skipping <name>-peer-pods-credentials-raw (openshift-sandboxed-containers-aws): delivered post-provision`. The target namespace does not exist at install time. |

A delivery value other than `post-provision` fails both tasks with `AccessKey <name> has unknown delivery '<value>'; update the pipeline image`.

### Provision

| Task | Behavior for a `coco` overlay |
|---|---|
| `scope-aws-credentials` | Substitutes the infra ID in the peer-pods policy, as in every labelled Policy. |
| `read-cluster-metadata` | Returns `podvm-instance-type`. A value that is not one instance type name fails the task. |
| `read-cluster-tier` | Accepts `coco`. A tier outside `base`, `virt`, `ai`, `coco` fails the task with `Tier '<tier>' is not supported by this pipeline image`. |
| `trigger-post-provision` | Passes `podvm-instance-type` to the post-provision PipelineRun and sets the PipelineRun timeout to 5 hours. |

### Post-provision

Three tasks run only for `tier=coco`, in this order, after `apply-base-workloads` and before `configure-spoke-rbac`: `prepare-podvm-aws`, `build-podvm-image-aws`, `apply-coco-workloads`.

The post-provision PipelineRun has a timeout of 5 hours (`spec.timeouts.pipeline`): 2 hours for `build-podvm-image-aws`, 2 hours for `apply-coco-workloads` and 1 hour for the other tasks. `trigger-post-provision` and the TriggerTemplate `post-provision-template` set it, and it applies to every tier.

`prepare-podvm-aws` runs on the hub with the cluster's installer credential (Secret `aws-credentials` in the cluster namespace):

1. Lists the spoke's nodes with the role `worker` and takes the first by name.
2. Reads that node's VPC, subnet and security groups from EC2.
3. Authorizes ingress on each of those security groups, with the same group as source, for `15150/tcp`, `9000/tcp` and `9000/udp`. Rules that already exist are left as they are.
4. Returns `region`, `vpc-id`, `subnet-id` and `sg-ids` as Tekton results.

`build-podvm-image-aws` (CLI `fleet-build-podvm-image-aws`) runs on the hub with the same credential. The names are in the table under [Pod VM image](#pod-vm-image). The Tekton task timeout is 2 hours.

1. Reads the operator's related images from the spoke's catalog and selects the disk image. Zero or several candidates fail the task.
2. Returns the newest available AMI of the account that carries both tags, when one exists. An AMI with a boot mode other than `uefi` or `uefi-preferred` fails the task.
3. Otherwise registers the AMI on a completed snapshot that carries both tags, when one exists.
4. Otherwise writes the spoke's pull secret (Secret `pull-secret` in `openshift-config`) to a file with mode 0600 in the scratch volume, extracts the disk file with `oc image extract`, and deletes the pull secret file.
5. Reads the disk format with `qemu-img info`, logs the file size and the virtual size, and converts a `qcow2` disk to raw. A raw disk is used as it is; any other format fails the task.
6. Creates the staging bucket and uploads the raw disk.
7. Starts the snapshot import with `ec2 ImportSnapshot`, polls the import task every 15 seconds for up to 60 minutes, and tags the snapshot.
8. Deletes the disk files, the uploaded object and the bucket, after a successful and after a failed build. A bucket deletion that fails is logged as a warning.
9. Registers the AMI.
10. Returns `ami-id` and `podvm-payload` as Tekton results.

`apply-coco-workloads` writes to the spoke in this order and stops at the first failure:

1. Fails when `podvm-instance-type` is empty or when the package `sandboxed-containers-operator` is not in the `redhat-operators` catalog with channel `stable`.
2. Namespace `openshift-sandboxed-containers-operator`.
3. Secret `peer-pods-secret` with `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, read from `<name>-peer-pods-credentials-raw` on the hub. The values reach `oc` on stdin. The Secret exists before the operator runs, so the operator creates no CredentialsRequest.
4. ConfigMap `osc-feature-gates` with `confidential: "true"`.
5. ConfigMap `peer-pods-cm` (see [peer-pods-cm values](#peer-pods-cm-values)).
6. OperatorGroup and Subscription (`stable`, automatic approval); waits up to 15 minutes for the ClusterServiceVersion to reach `Succeeded`.
7. Pairing check: reads `status.installedCSV` of the Subscription and the related images of that ClusterServiceVersion. The task fails with `re-run post-provision` when the disk image of the installed version has a digest other than `podvm-payload`.
8. KataConfig `example-kataconfig` with `enablePeerPods: true`. Every node reboots once. The task polls every 30 seconds, for up to 90 minutes, until the KataConfig is installed on every node, the DaemonSet `osc-caa-ds` exists and the RuntimeClass `kata-remote` exists. A node listed under `failedToInstall` fails the task at once. The Tekton task timeout is 2 hours.

The manifests of steps 2, 4, 6 and 8 are in `workloads/coco/`.

### Deprovision

`terminate-pod-vms` runs before `delete-cluster-resources`. `openshift-install destroy` does not find pod VMs, because they carry only the tag `openshiftpartnerlabs.com/cluster=<name>`. A pod VM that is left running keeps a network interface in the cluster subnet.

1. Reads the ManagedCluster tier label. For a tier other than `coco`, or when the cluster is not installed, the task ends without a change.
2. Deletes the AccessKey `<name>-peer-pods-access-key` and waits up to 120 seconds for it to be gone, so that cloud-api-adaptor can launch no new pod VM.
3. Lists the pod VMs every 10 seconds and terminates them until none is left. A pod VM is an instance that is not yet terminated, carries `openshiftpartnerlabs.com/cluster=<name>` or `kubernetes.io/cluster/<infraID>=owned`, and has no IAM instance profile. Cluster nodes always have an instance profile.
4. Fails after 10 minutes (`timeout-seconds`) with one error line per remaining instance.
5. Deregisters every AMI of the account that carries `openshiftpartnerlabs.com/cluster=<name>` and the tag key `openshiftpartnerlabs.com/podvm-payload`, and deletes the snapshots of those AMIs and every snapshot that carries both tags. Snapshots of persistent volumes carry the cluster tag only and are left to the uninstall.
6. Deletes the object `podvm.raw` and the bucket `<infraID>-podvm-image` when the bucket exists.

Nothing else is deleted when the task fails; re-run deprovision.

`cleanup-hub-artifacts` deletes the peer-pods User, Policy and UserPolicyAttachment by the ownership label, as it does for the operators' IAM resources.

## peer-pods-cm values

| Key | Value | Source |
|---|---|---|
| `CLOUD_PROVIDER` | `aws` | fixed |
| `VXLAN_PORT` | `9000` | fixed |
| `PROXY_TIMEOUT` | `8m` | fixed |
| `PODVM_INSTANCE_TYPE` | for example `m6a.large` | `podvm-instance-type` in `metadata.yaml` |
| `PODVM_INSTANCE_TYPES` | same as `PODVM_INSTANCE_TYPE` | `podvm-instance-type` in `metadata.yaml` |
| `PODVM_AMI_ID` | AMI ID | `build-podvm-image-aws` |
| `AWS_REGION` | cluster region | ClusterDeployment `spec.platform.aws.region` |
| `AWS_SUBNET_ID` | subnet of the first worker node | `prepare-podvm-aws` |
| `AWS_VPC_ID` | VPC of the first worker node | `prepare-podvm-aws` |
| `AWS_SG_IDS` | all security groups of the first worker node, comma-separated | `prepare-podvm-aws` |
| `TAGS` | `openshiftpartnerlabs.com/cluster=<name>` | cluster name |
| `PEERPODS_LIMIT_PER_NODE` | `10` | fixed |
| `ROOT_VOLUME_SIZE` | `6` | fixed |
| `DISABLECVM` | `false` | fixed; the operator rewrites the key from `osc-feature-gates` on every reconcile |

`INITDATA` is not set.

## Run a workload in a pod VM

Set the RuntimeClass on the pod:

```yaml
spec:
  runtimeClassName: kata-remote
```

Check on the spoke that the runtime is installed:

```bash
oc get kataconfig example-kataconfig -o jsonpath='{.status.kataNodes.readyNodeCount}/{.status.kataNodes.nodeCount}{"\n"}'
```

```bash
oc get runtimeclass kata-remote
```

```bash
oc get daemonset osc-caa-ds -n openshift-sandboxed-containers-operator
```

## Failure messages

| Task | Message | Action |
|---|---|---|
| `prepare-podvm-aws` | `no node with role worker on the spoke` | No node of the spoke has the label `node-role.kubernetes.io/worker`; check `oc get nodes` on the spoke. |
| `build-podvm-image-aws` | `no related image of repository openshift-sandboxed-containers/osc-dm-verity-image pinned by digest` | The operator version in the spoke's catalog names no such image. The message lists its related images. |
| `build-podvm-image-aws` | `/image/podvm.qcow2 not found in <image>` | The disk has another file name in that operator version. The message lists the extracted files; the expected name is `PODVM_DISK_FILE` in `fleet/tasks/_podvm_image_aws.py`. |
| `build-podvm-image-aws` | `oc image extract <image> failed` | The message carries the `oc` error. Check that the spoke's pull secret has access to the registry of the disk image and that the hub reaches it. |
| `build-podvm-image-aws` | `qemu-img convert failed` with `No space left on device` | The hub node's ephemeral storage is smaller than the disk file plus its virtual size; the task logs both sizes before the conversion. |
| `build-podvm-image-aws` | `An error occurred (<code>) when calling the ImportSnapshot operation` | Check that the role `<name>-vmimport-role` exists and that the installer policy has `iam:PassRole` on it. An overlay rendered before fleet-cluster-scaffold created the role has neither; regenerate the overlay. |
| `build-podvm-image-aws` | `import task <id> is deleted: <message>` | AWS rejected the disk; the message is the import task's status message. |
| `build-podvm-image-aws` | `import task <id> did not complete within 3600 s` | Re-run post-provision. |
| `build-podvm-image-aws` | `AMI <ami> has boot mode '<mode>'` | An AMI with both tags has another boot mode. Deregister it, then re-run post-provision. |
| `build-podvm-image-aws` | `AMI name <ami-name> is taken by an image without the tags` | Deregister the image of that name, or set both tags on it, then re-run post-provision. |
| `apply-coco-workloads` | `The pod VM AMI was built from disk image <payload>; <csv> uses <image>; re-run post-provision` | The installed operator version is another version than the catalog named when the AMI was built. Re-run post-provision when `installedCSV` and `currentCSV` of the Subscription are equal. |
| `apply-coco-workloads` | `Subscription sandboxed-containers-operator has no installedCSV; re-run post-provision` | Re-run post-provision. |
| `apply-coco-workloads` | `podvm-instance-type is empty` | Regenerate the overlay with the current fleet-cluster-scaffold and `--tier coco`. |
| `apply-coco-workloads` | `expected 1 peer-pods credential` | Regenerate the overlay with the current fleet-cluster-scaffold. |
| `terminate-pod-vms` | `pod VM <id> is still <state> after <n>s` | Terminate the instance in EC2, then re-run deprovision. |
| `terminate-pod-vms` | `An error occurred (<code>) when calling the DeregisterImage`, `DeleteSnapshot` or `DeleteBucket` `operation` | Re-run deprovision; the task repeats the deletion. For `BucketNotEmpty`, empty the bucket `<infraID>-podvm-image` first. |

## Limits

- Red Hat's OSC 1.13 support matrix has no entry for confidential containers on AWS.
- No attestation service is deployed and no initdata is set.
- The OSC AWS guide requires a worker node; compact and sno use the operator's converged-cluster path.
- The Subscription upgrades automatically. An operator upgrade does not rebuild the AMI; `peer-pods-cm` keeps the AMI of the earlier version until post-provision runs again.
- A post-provision re-run that builds a new AMI writes its ID to `peer-pods-cm` and does not restart `osc-caa-ds`.
- An AMI of an earlier disk image is deleted only by deprovision.
- A KataConfig deletion on the spoke runs the operator's image deletion Job against the cluster's AMI; the peer-pods policy denies it.
- The scratch volume of `build-podvm-image-aws` has no size limit.
- `qemu-img` in the pipeline image comes from CentOS Stream 9 AppStream; UBI 9 does not ship it, and the package is outside Red Hat's support for UBI content. The image build pins the CentOS signing key file by SHA-256; a changed key file fails the build (see [developer-guide.md](developer-guide.md#maintenance-centos-signing-key)).
- No pipeline run has verified these: the file name and the size of the disk in the disk image, the duration of the snapshot import, and the launch of a TPM 2.0 AMI with AMD SEV-SNP.
- Pod VMs run in one availability zone, with all security groups of the first worker node.
- The unit tests replace `oc`, `qemu-img`, EC2 and S3; no test runs against the operator or AWS.
