# Confidential containers tier (`coco`)

The `coco` tier installs OpenShift sandboxed containers with peer pods on an AWS cluster. A pod that uses the RuntimeClass `kata-remote` runs in its own EC2 instance (a pod VM) with AMD SEV-SNP. This page is for operators who provision and deprovision `coco` clusters through the fleet pipelines.

The cluster overlay is generated by [fleet-cluster-scaffold](https://github.com/redhat-openshift-partner-labs/fleet-cluster-scaffold) with `--tier coco`. Its README section "Confidential containers tier (--tier coco)" describes the overlay, the peer-pods IAM policy and the pipeline contract that the tasks below implement.

## Prerequisites

| Prerequisite | Requirement |
|---|---|
| OpenShift version | 4.22.11 or later on 4.22, or 4.21.24 or later on 4.21. The scaffold default image set `img4.22.22-multi-appsub` meets it. A custom `--image-set` is not checked. |
| Region | `us-east-2` or `eu-west-1`. The scaffold rejects other regions. |
| Pod VM AMI | One AMI per region, in the AWS account the clusters install into. See [Pod VM AMI](#pod-vm-ami). |
| Hub | The Tekton definitions under `tekton/` and the pipeline image (`pipeline-image` in `fleet-pipeline-config`) include the `coco` tasks before a `coco` overlay is merged into fleet-clusters. |

### Pod VM AMI

fleet does not build the AMI. `prepare-podvm-aws` looks it up in the cluster's region and fails when it is missing or unusable. The AMI must meet all of these:

- owned by the account the clusters install into;
- state `available`;
- boot mode `uefi` or `uefi-preferred` (AMD SEV-SNP requires UEFI);
- tag `openshiftpartnerlabs.com/podvm-image=true` on the AMI and on every backing snapshot. The cluster's peer-pods IAM policy allows instance launches only from images and snapshots that carry the tag;
- built from the pod VM disk of the OpenShift sandboxed containers version that the `stable` channel installs.

The build steps are in `aws-podvm-image-handler.sh` under `config/peerpods/podvm/` in [openshift/sandboxed-containers-operator](https://github.com/openshift/sandboxed-containers-operator).

Tag an existing AMI and its snapshots:

```bash
aws ec2 create-tags --region us-east-2 --resources <ami-id> <snapshot-id> --tags Key=openshiftpartnerlabs.com/podvm-image,Value=true
```

List the AMIs that `prepare-podvm-aws` considers in a region. When several match, the task takes the one with the latest `CreationDate`:

```bash
aws ec2 describe-images --region us-east-2 --owners self --filters "Name=tag:openshiftpartnerlabs.com/podvm-image,Values=true" "Name=state,Values=available" --query 'Images[].[ImageId,CreationDate,BootMode]' --output table
```

## Create the overlay

```bash
fleet-scaffold-cluster aws --name coco-east-01 --region us-east-2 --tier coco --podvm-instance-type m6a.xlarge
```

Compared with a scoped overlay of another tier, a `coco` overlay has:

- one more Crossplane AccessKey, `<name>-peer-pods-access-key`, which writes the Secret `<name>-peer-pods-credentials-raw` on the hub. It carries the three target annotations (`credentials-request: openshift-sandboxed-containers-aws`, `target-namespace: openshift-sandboxed-containers-operator`, `target-secret: peer-pods-secret`) and `openshiftpartnerlabs.com/delivery: post-provision`;
- the key `podvm-instance-type` in `metadata.yaml` (see [per-cluster-metadata.md](per-cluster-metadata.md));
- the ManagedCluster label `tier: coco`.

## What the pipelines do

### Pre-provision

| Task | Behavior for a `coco` overlay |
|---|---|
| `wait-for-aws-component-credentials` | Waits for `<name>-peer-pods-credentials-raw` together with the operators' raw Secrets. |
| `build-aws-credentials-manifests` | Leaves the peer-pods credential out of `<name>-cloud-credentials-manifests` and logs `Skipping <name>-peer-pods-credentials-raw (openshift-sandboxed-containers-aws): delivered post-provision`. The target namespace does not exist at install time. |

A delivery value other than `post-provision` fails both tasks with `AccessKey <name> has unknown delivery '<value>'; update the pipeline image`.

### Provision

| Task | Behavior for a `coco` overlay |
|---|---|
| `scope-aws-credentials` | Substitutes the infra ID in the peer-pods policy, as in every labelled Policy. |
| `read-cluster-metadata` | Returns `podvm-instance-type`. A value that is not one instance type name fails the task. |
| `read-cluster-tier` | Accepts `coco`. A tier outside `base`, `virt`, `ai`, `coco` fails the task with `Tier '<tier>' is not supported by this pipeline image`. |
| `trigger-post-provision` | Passes `podvm-instance-type` to the post-provision PipelineRun. |

### Post-provision

Both tasks run only for `tier=coco`, after `apply-base-workloads` and before `configure-spoke-rbac`.

`prepare-podvm-aws` runs on the hub with the cluster's installer credential (Secret `aws-credentials` in the cluster namespace):

1. Lists the spoke's nodes with the role `worker` and takes the first by name.
2. Reads that node's VPC, subnet and security groups from EC2.
3. Finds the pod VM AMI by tag and checks its boot mode and snapshot tags.
4. Authorizes ingress on each of those security groups, with the same group as source, for `15150/tcp`, `9000/tcp` and `9000/udp`. Rules that already exist are left as they are.
5. Returns `region`, `vpc-id`, `subnet-id`, `sg-ids` and `ami-id` as Tekton results.

`apply-coco-workloads` writes to the spoke in this order and stops at the first failure:

1. Fails when `podvm-instance-type` is empty or when the package `sandboxed-containers-operator` is not in the `redhat-operators` catalog with channel `stable`.
2. Namespace `openshift-sandboxed-containers-operator`.
3. Secret `peer-pods-secret` with `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, read from `<name>-peer-pods-credentials-raw` on the hub. The values reach `oc` on stdin. The Secret exists before the operator runs, so the operator creates no CredentialsRequest.
4. ConfigMap `osc-feature-gates` with `confidential: "true"`.
5. ConfigMap `peer-pods-cm` (see [peer-pods-cm values](#peer-pods-cm-values)).
6. OperatorGroup and Subscription (`stable`, automatic approval); waits up to 15 minutes for the ClusterServiceVersion to reach `Succeeded`.
7. KataConfig `example-kataconfig` with `enablePeerPods: true`. Every node reboots once. The task polls every 30 seconds, for up to 90 minutes, until the KataConfig is installed on every node, the DaemonSet `osc-caa-ds` exists and the RuntimeClass `kata-remote` exists. A node listed under `failedToInstall` fails the task at once. The Tekton task timeout is 2 hours.

The manifests of steps 2, 4, 6 and 7 are in `workloads/coco/`.

### Deprovision

`terminate-pod-vms` runs before `delete-cluster-resources`. `openshift-install destroy` does not find pod VMs, because they carry only the tag `openshiftpartnerlabs.com/cluster=<name>`. A pod VM that is left running keeps a network interface in the cluster subnet.

1. Reads the ManagedCluster tier label. For a tier other than `coco`, or when the cluster is not installed, the task ends without a change.
2. Deletes the AccessKey `<name>-peer-pods-access-key` and waits up to 120 seconds for it to be gone, so that cloud-api-adaptor can launch no new pod VM.
3. Lists the pod VMs every 10 seconds and terminates them until none is left. A pod VM is an instance that is not yet terminated, carries `openshiftpartnerlabs.com/cluster=<name>` or `kubernetes.io/cluster/<infraID>=owned`, and has no IAM instance profile. Cluster nodes always have an instance profile.
4. Fails after 10 minutes (`timeout-seconds`) with one error line per remaining instance. Nothing else is deleted when the task fails; re-run deprovision.

`cleanup-hub-artifacts` deletes the peer-pods User, Policy and UserPolicyAttachment by the ownership label, as it does for the operators' IAM resources.

## peer-pods-cm values

| Key | Value | Source |
|---|---|---|
| `CLOUD_PROVIDER` | `aws` | fixed |
| `VXLAN_PORT` | `9000` | fixed |
| `PROXY_TIMEOUT` | `8m` | fixed |
| `PODVM_INSTANCE_TYPE` | for example `m6a.large` | `podvm-instance-type` in `metadata.yaml` |
| `PODVM_INSTANCE_TYPES` | same as `PODVM_INSTANCE_TYPE` | `podvm-instance-type` in `metadata.yaml` |
| `PODVM_AMI_ID` | AMI ID | `prepare-podvm-aws`, by tag |
| `AWS_REGION` | cluster region | ClusterDeployment `spec.platform.aws.region` |
| `AWS_SUBNET_ID` | subnet of the first worker node | `prepare-podvm-aws` |
| `AWS_VPC_ID` | VPC of the first worker node | `prepare-podvm-aws` |
| `AWS_SG_IDS` | all security groups of the first worker node, comma-separated | `prepare-podvm-aws` |
| `TAGS` | `openshiftpartnerlabs.com/cluster=<name>` | cluster name |
| `PEERPODS_LIMIT_PER_NODE` | `10` | fixed |
| `ROOT_VOLUME_SIZE` | `6` | fixed |
| `DISABLECVM` | `false` | fixed; the operator rewrites the key from `osc-feature-gates` on every reconcile |

`INITDATA` is not set.

## Run a workload in a pod VM

Set the RuntimeClass on the pod:

```yaml
spec:
  runtimeClassName: kata-remote
```

Check on the spoke that the runtime is installed:

```bash
oc get kataconfig example-kataconfig -o jsonpath='{.status.kataNodes.readyNodeCount}/{.status.kataNodes.nodeCount}{"\n"}'
```

```bash
oc get runtimeclass kata-remote
```

```bash
oc get daemonset osc-caa-ds -n openshift-sandboxed-containers-operator
```

## Failure messages

| Task | Message | Action |
|---|---|---|
| `prepare-podvm-aws` | `no pod VM AMI tagged openshiftpartnerlabs.com/podvm-image=true in <region>` | Build or tag the AMI in that region, then re-run post-provision. |
| `prepare-podvm-aws` | `AMI <ami> has boot mode '<mode>'` | Register the AMI with boot mode `uefi` or `uefi-preferred`. |
| `prepare-podvm-aws` | `snapshot <snap> of AMI <ami> lacks tag` | Tag the snapshot. |
| `prepare-podvm-aws` | `no node with role worker on the spoke` | No node of the spoke has the label `node-role.kubernetes.io/worker`; check `oc get nodes` on the spoke. |
| `apply-coco-workloads` | `podvm-instance-type is empty` | Regenerate the overlay with the current fleet-cluster-scaffold and `--tier coco`. |
| `apply-coco-workloads` | `expected 1 peer-pods credential` | Regenerate the overlay with the current fleet-cluster-scaffold. |
| `terminate-pod-vms` | `pod VM <id> is still <state> after <n>s` | Terminate the instance in EC2, then re-run deprovision. |

## Limits

- Red Hat's OSC 1.13 support matrix has no entry for confidential containers on AWS.
- No attestation service is deployed and no initdata is set.
- The OSC AWS guide requires a worker node; compact and sno use the operator's converged-cluster path.
- The pod VM AMI is not paired with the operator version; the Subscription upgrades automatically.
- A KataConfig deletion on the spoke runs the operator's image deletion Job against the shared AMI; the peer-pods policy denies it.
- A re-run that changes peer-pods-cm does not restart osc-caa-ds.
- A missing AMI is found by prepare-podvm-aws, after the install: metadata.yaml carries no region.
- Pod VMs run in one availability zone, with all security groups of the first worker node.
- The unit tests replace oc and EC2; no test runs against the operator.
